STEP 0 — PARSE THE SOURCE DATA (write and run real code, verify your own output 
before building UI on top of it)                                                
                                                                                
Two files define the content, and they must be joined together:                 
- @"Nurturing green.json" — raw Lucidchart shape/line export. Schema:           
pages[0].items.shapes (array of {id, class, textAreas: [{label, text}]}),       
pages[0].items.lines (connectivity only, not reliable for grouping — do not use 
this for section membership).                                                   
- @"Nurturing green.csv"  — the actual source of truth for structure. Columns   
include: Id (row id), Name (shape type, e.g. "Process", "Decision", "Sticky     
note", "SparkFrameBlock", "Terminator"), Contained By (parent row Id — this is  
real geometric containment), Text Area 1–96 (actual text content), Shape ID     
(join key back to the JSON's shape id field).                                   
                                                                                
Join logic:                                                                     
1. Normalize both ID sets by stripping zero-width-space characters (\u200b)     
before comparing — the CSV export adds these to some Shape ID values, the JSON  
does not have them. After stripping, CSV "Shape ID" matches JSON "id" for ~99%  
of shapes.                                                                      
2. For every row, walk up the "Contained By" chain (row → its container → that  
container's container, etc., max ~20 levels to avoid cycles) until you hit a    
row where Name == "SparkFrameBlock". That frame's text is the row's section. If 
you reach a row with no Contained By value before finding a SparkFrameBlock,    
the row is UNRESOLVED — do not guess, do not attach it to the nearest-sounding  
name. Put it in a separate "unsorted" list.                                     
3. Deduplicate section names for known typos only (do not invent new            
groupings): "Ouick Com" → "Quick Com", "Purchase Planing" → "Purchase           
Planning", "Dicount Process" → "Discount Process". Drop rows where Name ==      
"SparkFrameBlock" and text is empty or literally "Add title" — these aren't     
real sections.                                                                  
4. Preserve section order as first-appearance order by row Id in the CSV        
(ascending), not alphabetical, not re-grouped by topic.                         
                                                                                
Content-type classification, by the CSV's "Name" column:                        
- VIDEO-PLACEHOLDER topic: Name in {Process, Preparation, Database, Internal    
storage, Manual input, Display, Block} — these are demonstrable actions.        
- FLOWCHART-ONLY node (never a video): Name in {Decision, Terminator, Delay} —  
branch logic, end-states, wait conditions. Render as an actual interactive      
flowchart (real boxes/diamonds/terminators, real connecting lines via the       
JSON's lines data where available, real step text) — not a mockup.              
- REFERENCE CALLOUT attached to the nearest topic: Name in {Sticky note, Text,  
MinimalTextBlock} — show as an expandable "Notes" panel on the relevant topic,  
not as its own lesson.                                                          
- SUPPORTING VISUAL: Name == "User Image" — attach as a reference image on the  
nearest topic.                                                                  
                                                                                
Output this parsing pass as a clean content.json (section → topic list, each    
topic tagged type: "video" | "flowchart", with notes/image fields as            
applicable) plus a separate unsorted.json for anything that didn't resolve. Use 
content.json as the only data source the front-end renders from — don't         
re-parse the raw files at render time. Print a summary count (resolved vs.      
unsorted, per-section topic counts) so I can sanity-check it before you build   
UI on top of it.                                                                
                                                                                
Known data gap, don't try to fix it silently: the "Outward" section will        
resolve to almost no content — its real content sits in unattached containers   
and is currently unresolved. Leave it thin and visible as thin, don't pad it or 
reassign unresolved content into it by guessing.

  per course — a mechanical transcription, not a course. Redo this: for each    
  resolved section, read all its topics in sequence (order by the JSON's line   
  connectivity within that section where available, otherwise by CSV row Id)    
  and actually understand what task is being described before deciding where a  
  video starts and ends.

  continuous task — same tool, same immediate goal, no branch or handoff in     
  between. Example: "Open Seller Portal" → "Go to PO Management" → "Click       
  Download" → "Save the file" is ONE video: "Download the Bulk PO Report from   
  the Seller Portal." Not four.                                                 
                                                                                
  Start a NEW lesson only when one of these actually happens: a Decision/branch 
  point, a change in who's responsible for the action (e.g. Sales team hands    
  off to Warehouse team), a change in which system/tool is being used, or a     
  genuine milestone that closes one phase before the next begins (e.g. "PO      
  Confirmed" before dispatch steps start).

  count. If a course still needs 15+ lessons after honestly applying this rule, 
  that's fine — some processes are just long — but it should be because the     
  content genuinely has that many distinct phases, not because you didn't       
  merge.                                                                        
                                                                                
  PROBLEM 2 — Course names are raw internal labels, not real names              
  "Critical," "Suppression," and similar are not course titles — they're        
  whatever shorthand the original diagram author used. For every course, read

  raw label as a small internal reference tag (for cross-checking against the   
  source file), but the title a user sees must be descriptive.

  will happen for a few — some sections have under 10 shapes), do not invent a  
  plausible-sounding name anyway. Mark it explicitly: "Needs clarification —    
  unclear scope" with a one-line note on what little content exists. A wrong    
  confident name is worse than an honest flag.
